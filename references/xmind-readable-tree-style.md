# XMind 可读业务树风格

历史 GEO 用例库里的 XMind 更像“可执行的产品检查树”，不是测试表格的脑图版。生成 XMind 时优先让熟悉旧用例的人能按页面和操作快速扫读。

## 层级顺序

优先使用以下层级，缺少某层时直接跳过：

1. 根节点：功能、页面或业务范围，例如 `新增人员`、`全球政策查询`。
2. 一级节点：产品端、入口、端类型、主页面区域或主步骤，例如 `pc端`、`移动端`、`入口`、`step1.请选择服务产品`。
3. 二级节点：字段、按钮、卡片、tab、列表、弹窗、状态，例如 `手机号`、`提交`、`合作产品卡片`。
4. 三级及以下：条件、校验、提示文案、数据来源、数据落点、状态变化、异常分支和最终结果。

## 节点命名

- 使用业务对象和界面文案作节点名，例如 `点击[登录]`、`前端输入校验`、`toast提示：提交成功`。
- 把条件写成可读判断，例如 `工作所在国家/地区：为空`、`合同已过期、已终止`。
- 把结果挂在触发动作或条件下面，例如 `点击立即提交 -> 提交成功，toast提示“提交成功”并关闭弹窗`。
- 数据落点用明确节点承载，例如 `GEO业务系统-客户中心-官网线索 -> 新增一条数据`。

## 不要这样做

- 不要把每条用例固定展开成 `测试步骤：...`、`预期结果：...`、`优先级：...`、`测试类型：...`。
- 不要把长步骤合成一个超长叶子；应拆成动作、条件、校验、结果。
- 不要为了字段完整性牺牲阅读路径；优先让测试人员能沿着页面操作读下去。

## 简短示例

推荐：

```text
登录
  账号
    输入框中的默认提示文字
      请输入手机号/工号/邮箱
    前端输入校验
      必填
        不填，点击登录时下方红字提示：请输入手机号/工号/邮箱
  点击[登录]
    校验账号是否存在
      不存在直接toast提示：用户名与密码不匹配
      存在则进行密码校验
    登录后验证
      跳转到第一个一级菜单下
```

不推荐：

```text
登录
  正向场景
    输入正确账号密码登录
      测试步骤：输入账号；输入密码；点击登录
      预期结果：登录成功
      优先级：P1
      测试类型：功能
```
